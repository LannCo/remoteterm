### R4-COV-1 [LOW] `preventDefault` on NumberControl spin-button mousedown is untested for its actual effect (`generalcontent.tsx:1162,1171`)
- Reverted just the two `onMouseDown={(e) => e.preventDefault()}` calls, kept everything else at HEAD: all 9 `generalcontent-numbercontrol.test.tsx` tests stayed green.
- Confirmed why: `onControlBlur`'s `e.currentTarget.contains(e.relatedTarget as Node)` guard already prevents a premature commit when focus moves from the input to a spin button inside the same wrapper div, independent of whether the button ever received focus in the first place. `preventDefault` on mousedown suppresses that focus move entirely (keeps the input focused so a user can keep typing/using arrow keys after a spin click); the blur guard is what protects the write-ordering behaviour the fix commit's tests actually assert (`c.writes()`, `c.input().value`).
- Risk: in a real browser, removing `preventDefault` would move keyboard focus off the input to the spin button after every click — a real UX regression (losing the caret, arrow-key stepping stops working from the input) — but no test asserts `document.activeElement` after a spin click, so that regression would not be caught by this suite in either happy-dom or (per the fix author's own note) real-browser testing.
- Suggested test: assert `document.activeElement === c.input()` immediately after `await user.click(c.up())`, before any round-trip settles.
- Certainty: traced directly to the revert-and-rerun above (9/9 green with `preventDefault` removed, blur-guard code path confirmed by reading `onControlBlur`).

### R4-COV-3 [INFO] Real-timer-based NumberControl tests: bounded flake risk, not exercised under load
- `generalcontent-numbercontrol.test.tsx` uses real `setTimeout` (200ms/100ms/50ms, `setup({ delayMs })`) rather than `vi.useFakeTimers()`, and settles via `waitFor(..., { timeout: 3000 })` polling (`c.settled()`, `c.eventsLanded()`) rather than a fixed sleep-then-assert. The one assertion made immediately after `await user.click()` with no wait (`rapid plain spin clicks...`, line 131, `expect(c.input().value).toBe("15")`) is driven by a synchronous React state update inside the click handler, not by real-timer completion, so it does not race the 200ms RPC delay.
- Residual risk is bounded to the 3000ms `waitFor` timeout being exceeded under severe CI resource contention (the RPC delays used are all well under 300ms) — this is the generic class of flake risk any real-timer async test carries, not something specific to a bug in these tests. Not exercised here under artificial load, so this is a plausibility assessment rather than a reproduced flake.
- Not fixing this is a reasonable call: `vi.useFakeTimers()` would need `vi.advanceTimersByTimeAsync()` interleaved with `userEvent`'s own internal timers (user-event schedules its own delays), which is a known source of hangs in this combination — the real-timer + generous-`waitFor` pattern is the safer trade-off, not an oversight.
- Certainty: traced to the test file's timer usage and `waitFor` timeout values directly; the flake-risk severity itself is an assessment, not a measurement, since reproducing CI-load flakiness is out of scope for this pass.
