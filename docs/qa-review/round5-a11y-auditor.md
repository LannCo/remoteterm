### [High] R5-A11Y-1: New focus-anchor containers are focusable, unconditionally `outline-none`, and silently steal focus on any blank-area click
- **WCAG criterion:** 2.4.7 Focus Visible (Level AA)
- **Location:** `frontend/app/view/sourcecontrol/sourcecontrol.tsx:711` (`<div ref={containerRef} tabIndex={-1} className="... outline-none">`, wraps the entire source-control view: header, banner, file tree, diff/review panes) and `frontend/app/view/remotetermconfig/remotetermconfig.tsx:193` (`<div ref={contentRef} tabIndex={-1} className="... outline-none">`, wraps the entire config content pane)
- **Issue:** These two containers fix R4-A11Y-2 (focus was falling to `<body>` on banner dismiss) by giving `tabIndex={-1}` to a large wrapping `<div>` and calling `.focus()` on it. That correctly keeps focus inside the document, and the two Round-4/5 keyboard-dismiss tests (`sourcecontrol-revert-error.test.tsx`, `remotetermconfig-dismiss-focus.test.tsx`) confirm `document.activeElement` lands there. But two problems follow from making a large content wrapper focusable this way:
  1. The class list is bare `outline-none` (not `focus:outline-none focus:border-*`, the replacement-indicator pattern this codebase already uses correctly on every focusable input, e.g. `secretscontent.tsx:147`, `generalcontent.tsx:1032`, `sourcecontrol.tsx:227`). There is no border, box-shadow, or other visual change on focus. Confirmed empirically: a scratch happy-dom render of `<div tabIndex={-1} className="outline-none" />`, focused, has `getComputedStyle(el).outline === ""`, `.border === ""`, `.boxShadow === ""` — no visible indicator exists at all, not merely a low-contrast one.
  2. `tabIndex={-1}` makes an element a valid *click*-focus target per the HTML spec's focusing steps, even though it's excluded from Tab order. Confirmed empirically in a scratch happy-dom + `@testing-library/user-event` test: clicking non-interactive text inside a `tabIndex={-1}` container (with a `<button>` focused elsewhere beforehand) moves `document.activeElement` to the container. Since both real containers wrap large areas of mostly-static content (headers, list rows' surrounding padding, diff gutters, etc.), **any click on whitespace anywhere in the source-control view or the config content pane silently relocates keyboard focus to an invisibly-focused, unlabelled div** — not just the banner-dismiss path these containers were added for.
- **Impact:** Sighted keyboard users (including those with low vision or motor impairment who mix pointer and keyboard) lose all visual track of focus the moment they click blank space in either panel: there is no ring, border, or highlight showing focus moved, and their next Tab/Shift+Tab starts from an unexpected point with no warning. This is broader than the dismiss flow the fix targeted — it fires on ordinary clicks unrelated to the error banners.
- **Fix:** Two independent fixes, both needed:
  - Give these containers a visible focus style, matching the codebase's existing pattern, e.g. `focus-visible:outline focus-visible:outline-accent focus-visible:outline-offset-[-1px]` (or reuse the `focus:border-accent` treatment) instead of unconditional `outline-none`. Use `focus-visible:` rather than `focus:` so the *programmatic* dismiss-focus case (which should always show, since it's not a mouse click) still renders it — `:focus-visible` matches programmatic `.focus()` calls made outside a click handler; confirm this holds for the browser/Electron Chromium version in use before relying on it as the sole gate.
  - Narrow the focusable surface so ordinary blank-area clicks don't capture it: either move `tabIndex={-1}` off the large wrapper onto a small dedicated anchor placed right after the banner (e.g. an `<h2>`-level heading or the panel's own header row) and point `focusAnchorRef`/`contentRef` at that instead, or keep the click-to-focus behaviour but give the container an `aria-label` (e.g. `aria-label="Source control"` / `aria-label="Configuration"`) so a screen-reader user who lands there at least hears where they are.

### [Info] R5-A11Y-2: Focus-anchor containers have no accessible name
- **WCAG criterion:** 4.1.2 Name, Role, Value (Level A) — advisory, not a clear-cut violation since a generic wrapper `<div>` is not itself a "UI component" the SC squarely targets; flagged for orientation impact rather than as a hard failure
- **Location:** Same two containers as R5-A11Y-1.
- **Issue:** Neither container has a `role`, `aria-label`, or `aria-labelledby`. When focus lands there (via keyboard-dismiss or the blank-click case in R5-A11Y-1), a screen reader has nothing to announce beyond possibly silence or "blank" — the user gets no confirmation of where they landed relative to the file they were viewing.
- **Impact:** Screen-reader users lose orientation context after dismissing a banner or after any blank-area click; they must explore manually to relocate themselves.
- **Fix:** If R5-A11Y-1's container-narrowing option isn't taken, add `aria-label` to the container (or promote it to a landmark, e.g. `role="region" aria-label="Source control"` for `sourcecontrol.tsx:711`, `role="region" aria-label="Configuration"` for `remotetermconfig.tsx:193`) so focus arriving there is announced.
