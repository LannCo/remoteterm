### [HIGH] R3-CONF-3: Auto-merge-into-existing-destination directly contradicts RENAME_PLAN.md's "abort loudly, merge manually" instruction
- **Category:** divergent (plan-vs-fix-commit drift pattern, see agent memory `feedback_plan_vs_fix_commit_drift`)
- **Source says:** RENAME_PLAN.md:819-824 (Phase 2 step 7): "Handle the destination-already-exists case explicitly... empty directory... -> remove it, then move; **non-empty without the migration marker -> abort loudly and tell the user to merge manually** rather than attempting a move-onto-existing that `fs.renameSync` will reject."
- **Code does:** `emain/emain-platform.ts:293` `else if (spec.canMergeIntoDest?.(destEntries)) { mergeDataRoot(spec); return; }`, with `mergeTree` (`emain/emain-platform.ts:333`) and `mergeDataRoot` (`:358`) performing an automatic, never-overwriting recursive move for both the `config` root (`canMergeIntoDest: () => true`, line 427, unconditional) and the `data` root (`canMergeIntoDest: (destEntries) => destEntries.every(...EmainDataEntryNames)`, line 440, conditional on the destination only containing emain's own startup-written `logs/`/`rtapp.log`). Only the `legacy-home` root (`name: "legacy-home"`, line 447 onward) has no `canMergeIntoDest` and still hits the plan's original abort branch.
- **Impact:** this is a considered, tested (`emain-platform.test.ts` new cases), well-reasoned fix for a real self-inflicted bug (an earlier build's partial/skipped migration left a non-empty destination that then aborted on every subsequent launch) — the code side is very likely correct. But nobody updated RENAME_PLAN.md's Phase 2 step 7 text, so the plan now actively describes the wrong behaviour for two of three roots; a future contributor re-deriving migration behaviour from the plan (as the plan itself says future readers should do) would reintroduce the abort-only behaviour this fix removed.
- **Recommendation:** amend RENAME_PLAN.md:819-824 to describe the per-root split now implemented: config and data roots merge into a non-empty, unmarked destination (never overwriting existing destination files, reporting any left-behind legacy files once), legacy-home root still aborts loudly and asks for a manual merge.

### [MEDIUM] R3-CONF-4: SingletonLock-based quit/migrate gate is new user-visible behaviour absent from RENAME_PLAN.md's Concurrency handling
- **Category:** undocumented (against the plan, which is the applicable source of truth here)
- **Source says:** RENAME_PLAN.md:825-833, the plan's own "Concurrency" risk item for Phase 2 step 7, addresses only the two-processes-launched-close-together race, and specifies a purely internal, silent mitigation: "Wrap the move in try/catch; treat `ENOENT` on the source during the move as 'another process already did this' and re-check for the completion marker rather than crashing module evaluation." No dialog, no quit prompt, and no mention of detecting a *running legacy pre-rename instance* (as opposed to a second instance of the *new* app) appears anywhere in RENAME_PLAN.md (`grep -n "SingletonLock" RENAME_PLAN.md` returns zero hits).
- **Code does:** `emain/emain-platform.ts:160-191` (`checkLegacyInstanceRunning`) and `:206-242` (`resolveLegacyInstanceBlock`) read the legacy Electron app's `SingletonLock` symlink at `<appData>/waveterm/electron`, and when a live or possibly-live legacy instance is detected, block migration and show one of two new `dialog.showMessageBox` prompts; `emain/emain.ts:274` calls this before the server starts, per commit `0b33097c`.
- **Impact:** not a conformance violation against a contradicted instruction (as R3-CONF-3 is) — the plan simply never anticipated this scenario, so there's nothing to contradict. Flagging because it's real new user-facing UI (two dialog boxes, a forced quit path) that a plan reader would have no way to know exists.
- **Recommendation:** add this gate to RENAME_PLAN.md's Concurrency risk item (or a new Phase 2 sub-bullet) as a second, later-discovered concurrency hazard (racing the *legacy* app, not just a second instance of the new one) with its own mitigation description, so the plan stays a complete account of migration behaviour.
